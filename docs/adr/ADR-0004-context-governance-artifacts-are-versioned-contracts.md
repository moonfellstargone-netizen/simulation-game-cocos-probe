# ADR-0004：上下文治理文件必须随代码包版本化

## 状态

Accepted

## 背景

项目存在跨对话推进：规划对话负责推导，执行对话负责修改。若只把任务清单复制给执行对话，执行 AI 会缺失“为什么这样设计”的背景，容易在未覆盖边界中自行补全。

另一个流程风险是：代码包或开发日志包里的后续建议可能被误读为下一版授权目标，导致版本号、任务意图和执行指令没有强绑定。这样即使测试通过，也可能出现“执行包自洽，但做的不是规划目标”的问题。

## 决策

代码包必须版本化保存以下治理文件：

```text
docs/CODE_CONTEXT_INDEX.md
docs/adr/*.md
docs/module_contracts/*.contract.md
```

这些文件必须纳入 `arch:check` 和 `npm run check`。每次新增关键模块或长期架构决策时，应同步更新治理文件，而不是只写在聊天记录或日志包。

每个代码推进版本还必须由外部执行指令提供 Task Intent Lock。Task Intent Lock 必须明确目标版本、版本名称、本轮唯一目标、明确不是哪些任务、允许修改范围、禁止修改范围、规划依据，以及与代码包 / 开发日志包中“后续建议”的优先级关系。

后续建议不是授权目标；外部执行指令中的 Task Intent Lock 优先。如果同一版本号出现两个不同任务意图，必须停止执行并报告，不得自行合并。

当前任务上下文交接可以来自外部执行指令或开发日志包；代码包只保存执行端上下文治理规则、索引、ADR、模块契约卡和自动化检查，不长期保存每轮具体任务上下文、讨论记录、临时判断或历史执行指令全文。

## 后果

- 执行对话能通过有限上下文读取当前有效决策原因。
- 模块边界不再只依赖记忆。
- 后续代码生成前预检报告有稳定依据。
- 版本号、任务意图和执行指令之间建立显式绑定。
- 后续建议会被降权为候选方向，不能自动变成下一版授权目标。
- 可机器验证的上下文治理规则进入测试和架构检查，降低跨对话执行错位风险。

## 禁止项

- 把历史争论、废案、过程日志混入治理文件。
- 把每轮具体任务上下文、讨论记录、临时判断或完整执行指令长期写入代码包。
- 用 ADR 替代正式设计包规则。
- 用模块契约卡替代源码测试。
- 把后续建议当成下一版授权目标。
- 同一版本号出现两个不同任务意图时自行合并。
- 治理文件更新后不更新检查脚本。

## 验证

`tests/context-governance-contracts.test.mjs` 和 `tools/validate_code_architecture.py` 必须检查治理文件存在、Task Intent Lock 规则、后续建议降权、禁止具体任务上下文文件、ADR 引用路径真实性和关键边界语句。
